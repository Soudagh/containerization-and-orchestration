# stand-picker

агент, который подбирает тестовый стенд под задачу и после подтверждения человеком бронирует его и накатывает сборку.

## кейс

команда делает голосовых ассистентов для операторов связи: 6 разработчиков, 4 тестировщика и пул из 8 стендов для ручного тестирования. стенды отличаются конфигурацией - телефония, SIP-транк, диск, хранилища S3 и ClickHouse, версия платформы. сейчас, чтобы получить стенд под задачу, нужно спросить тестировщика: знание, какой стенд чем отличается и что на нём сейчас тестируется, живёт у них в головах. тестировщик отвлекается, разработчик ждёт.

что делает workflow:
1. вебхук - задача перешла в тест и сборка готова, или разработчик просит стенд
2. обычный шаг разбирает вебхук и читает текущие брони из SQLite
3. агент читает описания стендов, сопоставляет требования задачи с конфигурацией и бронями и предлагает стенд с объяснением - JSON {stand, mode, reason}
4. обычный шаг валидирует ответ агента
5. человек подтверждает выбор в форме n8n
6. обычный шаг атомарно проверяет, что стенд всё ещё свободен, и бронирует его условным UPDATE
7. мок деплоя - запись в журнал deployments и итоговое сообщение

агент только предлагает. инструментов на запись у него нет, бронирует и деплоит детерминированный код после подтверждения человека.

## что где лежит

| путь | что |
|---|---|
| docker-compose.yml | n8n, два MCP-сервера, Prometheus, blackbox exporter, Grafana |
| data/environments | описания 8 стендов свободным текстом - MCP filesystem, только чтение |
| data/db/reservations.db | брони стендов и журнал деплоев - MCP SQLite |
| tasks | тестовые вебхуки трёх задач |
| skills.md | know-how агента - системный промпт |
| workflow/stand-picker.json | экспорт workflow из n8n |
| monitoring | конфиги Prometheus, алерты, blackbox, провижининг и дашборд Grafana |

## toolkit агента

| инструмент | MCP-сервер | что делает |
|---|---|---|
| environments_list_directory | mcp-environments | список описаний стендов |
| environments_read_multiple_files | mcp-environments | читает описания разом |
| reservations_list_tables | mcp-reservations | какие таблицы есть в базе |
| reservations_read_query | mcp-reservations | SELECT для уточняющих запросов |

write_query у SQLite-сервера агенту не выдан - им пользуются только узлы «бронь» и «Деплой» после подтверждения.

## запуск

нужны Docker и Ollama на хосте.

```bash
ollama pull qwen3:8b
ollama serve                      # слушает 127.0.0.1:11434, n8n ходит к нему через host.docker.internal

docker compose up -d
```

дальше в n8n на http://127.0.0.1:5678:
1. создать аккаунт владельца
2. импортировать workflow/stand-picker.json
3. в узле Ollama Chat Model создать credential: Base URL `http://host.docker.internal:11434`
4. нажать Execute workflow и отправить задачу:

```bash
curl -X POST http://127.0.0.1:5678/webhook-test/stand-request \
  -H 'Content-Type: application/json' -d @tasks/VA-1210.json
```

5. ссылка на форму подтверждения появится в выходе узла Wait - открыть, подтвердить, workflow продолжится

проверить результат:

```bash
sqlite3 data/db/reservations.db "select * from reservations; select * from deployments;"
```

вернуть базу в исходное состояние после прогонов:

```bash
sqlite3 data/db/reservations.db "UPDATE reservations SET task=NULL, owner=NULL, build='5.7.3', until=NULL, note=NULL WHERE note LIKE '%агентом%'; DELETE FROM deployments;"
```

мониторинг: Grafana http://127.0.0.1:3000 - дашборд stand-picker открывается сразу, Prometheus и алерты http://127.0.0.1:9090/alerts.

## настройки модели, без которых не работает

| настройка | значение | зачем |
|---|---|---|
| Context Length | 16384 | по умолчанию у Ollama окно маленькое, при переполнении она молча отрезает начало диалога вместе с системным промптом |
| Temperature | 0.1 | подбор стенда - не творческая задача |
| Max Tokens to Generate | 3000 | qwen3 иногда зацикливается в рассуждениях, без потолка один ответ генерировался 11 минут |
| /no_think в конце промпта | | отвечает без блока рассуждений - быстрее и без петель |
| дата в системном промпте | `{{ $now }}`, поле в режиме Expression | модель не знает сегодняшнюю дату, без неё не работает правило про протухшие брони |

## алерты

метрики n8n - на уровне запуска целиком: n8n_workflow_execution_duration_seconds с лейблом status. Ollama и MCP метрик не отдают, их доступность проверяет blackbox.

| алерт | условие | severity | почему эта метрика |
|---|---|---|---|
| StandPickerRunsFailing | больше половины запусков за час неуспешны при минимум 2 запусках, 10m | critical | подбор сломан - задачи не уходят в тест. трафик редкий, поэтому доля за час, а не число за минуты |
| StandPickerDependencyDown | probe_success Ollama или любого MCP не 1, 3m | critical | без модели или MCP агент не работает ни для одной задачи |
| StandPickerSlowRuns | p95 длительности запуска за час больше 240 с, 5m | warning | нормальный прогон 1-2 минуты, дольше - модель ушла в петлю генерации или перегружена |

время ответа Ollama в алерт не взято: /api/version отвечает за миллисекунды, даже когда модель генерирует, и петлю не показывает. гистограмма длительности пишется при завершении запуска, поэтому зависший запуск виден в ней только благодаря потолку Max Tokens to Generate.

## ограничения и развитие

+ модель на 8b соблюдает жёсткие правила - брони, общий транк, старая платформа, - но мягкие вроде «бери самый простой стенд» не всегда. их страхует только человек на подтверждении
+ в n8n нет метрик по узлам и бизнес-итогу, поэтому конфликт брони, когда стенд успели занять, через /metrics не виден - его стоило бы считать отдельно, например писать счётчик из workflow
+ write_query не поддерживает параметры запроса, поэтому SQL склеивается в коде с экранированием и белым списком имён стендов
+ вебхук без аутентификации - в реальной установке нужен header auth или подпись от трекера
